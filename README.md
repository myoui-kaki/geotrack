# GeoTrack — Student & OSAS Administrator System

A school project (FastAPI + SQLite + React) for tracking off-campus
student boarding houses. The Student side and the OSAS Administrator
side are **completely separate logins and pages**, but they share one
backend and one database, the same way a single school system would
in production.

## How everything is separated

| | Student | OSAS Administrator |
|---|---|---|
| Login page | `/student/login` | `/osas/login` |
| Dashboard URLs | `/student/home`, `/student/status`, ... | `/osas/dashboard`, `/osas/verification`, ... |
| Backend routes | `/api/student/*` | `/api/osas/*` |
| Role stored in JWT | `"student"` | `"osas_admin"` |

There is no shared "pick your role" screen anywhere. If a student
account is used to log into the OSAS page (or vice versa), the
frontend rejects it immediately, **and** the backend independently
rejects any request to the wrong route group even if someone bypasses
the frontend entirely — see `require_student` / `require_osas_admin`
in `backend/auth.py`.

If a session token expires or becomes invalid mid-use, the app signs
the user out and returns them to the correct login page automatically,
instead of leaving them stuck on a page that keeps failing.

Reviews are anonymous on purpose: the API response for a review never
includes who wrote it (see `schemas.ReviewOut`), so both apps render
every review's author as **"Unknown"** — including the student's own
review, which they can still edit or delete because the frontend
separately knows (via `/api/student/my-reviews`) which ones are theirs,
without that identity ever appearing in the public review list.
Concerns work the opposite way — those *do* include the student's name
and email, because OSAS needs to know who to follow up with.

## What's included

**Account security**
- Strong password rule on registration (8+ characters, upper/lowercase,
  number, special character)
- Email format validation
- Login lockout: 5 failed attempts locks the account for 5 minutes

**Full CRUD**, not just create/read, on every resource: boarding houses,
reviews, status updates, concerns, and both OSAS and student accounts
all support update and delete where it makes sense (e.g. a student can
edit/delete their own review and status update; OSAS can edit/delete
any boarding house, account, or concern).

**Interactive map** (Leaflet + OpenStreetMap, real San Pablo City
coordinates), used in two places:
- OSAS dashboard: every student's most recent boarding house location,
  flagged students shown as a red pin, everyone else green
- Student app: a small map of their own boarding house on the home
  screen, and of whichever boarding house they're viewing in the
  directory

**OSAS dashboard features** (matching the full feature set): geo-tagged
student locations, flagged students panel, boarding house verification
queue with inline reviews, student reviews per boarding house, tally
reports (group by barangay / boarding house / gender / monthly status,
filterable by month, with a print button), and account management for
both OSAS staff and student accounts.

## Running it

### 1. Backend

```bash
cd backend 
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

python seed.py                  # creates geotrack.db with sample data
uvicorn main:app --reload       # runs on http://127.0.0.1:8000
```

Sample accounts created by `seed.py`:
- Student: `juan.delacruz@lspu.edu.ph` / `Student1!`
- Student: `maria.santos@lspu.edu.ph` / `Student1!`
- Student (flagged): `pedro.bautista@lspu.edu.ph` / `Student1!`
- OSAS Admin: `reyes.osas@lspu.edu.ph` / `OsasAdmin1!`

Interactive API docs (auto-generated by FastAPI): `http://127.0.0.1:8000/docs`

### 2. Frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev                     # runs on http://localhost:5173
```

Visit:
- `http://localhost:5173/student/login` for the Student app
- `http://localhost:5173/osas/login` for the OSAS Administrator app

Both need the backend running at the same time, since the frontend
calls `http://127.0.0.1:8000/api/...` (configured in `src/api/client.js`).

## Notes for the school report

- **Database**: SQLite via SQLAlchemy ORM. Tables: `users` (role column
  separates students/admins, plus login-lockout fields), `boarding_houses`
  (with latitude/longitude for the map), `status_updates`, `reviews`,
  `concerns`.
- **Auth**: passwords hashed with bcrypt and validated for strength on
  registration; sessions are stateless JWTs carrying the user's id and
  role; failed logins are rate-limited per account.
- **Role separation** is enforced at three layers: the URL/route the
  user is on, the React route guard (`ProtectedRoute`), and the FastAPI
  dependency on every endpoint (`require_student` / `require_osas_admin`)
  — so even a modified frontend can't reach the wrong role's data.
- **Map data**: boarding house coordinates are entered by OSAS when
  registering or editing a listing; a student's pin on the OSAS map
  comes from their most recent status update that links to a boarding
  house, so it moves automatically if they submit a "transferred" update.
